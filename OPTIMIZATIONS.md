### OMBRA-OPT-01: Link the Rust core with packed relative relocations (RELR)

- **What**: libobscuravpn_client.so has 30,371 R_AARCH64_RELATIVE relocations in a classic .rela.dyn table of 729,240 bytes (24 bytes each). It has no DT_RELR tag. The NDK r28 clang driver does not turn on RELR for Android. The APK stores the .so uncompressed, so these bytes go 1:1 into the APK and into the mapped file. Bionic reads DT_RELR from API 30, and minSdk is 36.
- **Where**: scripts/build-rust.zsh:95-106 (remap array and per-target CARGO_TARGET_<TRIPLE>_RUSTFLAGS export); scripts/build-rust.zsh:121-132 (output checks)
- **Change**: Add `-C link-arg=-Wl,--pack-dyn-relocs=relr` to the per-target RUSTFLAGS that line 106 exports. Cargo joins these flags with the 16 KB flags of .cargo/config.toml (docs/research/build.md section 6), so the vendored crate does not change. Optional: add one check after the LOAD Align check: `$LLVM_BIN/llvm-readelf -d $stripped | grep -q '(RELR)' || die ...`.
- **Benefit**: The .so and the release APK get about 720 KB smaller (estimate from the relocation offsets, not from a build). RELR needs 1,126 words (9,008 bytes) instead of 729,240 bytes. The release APK goes from 14.08 MB to about 13.36 MB (about -5 %, estimate). This is the largest size win that does not touch Rust source. When :vpn loads the core, the loader reads about 9 KB instead of 729 KB of relocation data. The load-time gain is small and not measured.
- **Evidence**: NDK r28 `llvm-readelf -d app/src/main/jniLibs/arm64-v8a/libobscuravpn_client.so`: RELASZ 729240, RELACOUNT 30371, no RELR tag; BIND_NOW and FLAGS_1 NOW present. `llvm-readelf -r`: 30,371 R_AARCH64_RELATIVE (0 unaligned), 14 GLOB_DAT, 146 JUMP_SLOT. RELR word count computed from the real offsets: 1,126. `unzip -lv app-release.apk`: libobscuravpn_client.so Stored 10,405,496 B, APK 14,076,421 B. In clang-19 the string '--pack-dyn-relocs=relr' is only in the Fuchsia driver. Owner precedent: MegaGlass-Android/scripts/build-sdk.sh:50 uses the same flag. No Ombra doc considers or rejects RELR. app/build.gradle.kts:142 makes the script a Gradle input. The new CARGO_TARGET_*_RUSTFLAGS value changes the cargo fingerprint of every crate for that target, so the next build compiles the full fat-LTO core again once, not only a relink.
- **Safety**: This is a linker flag in Ombra's own build script. The lines come from b8bff8c, not from a 'Report:' commit. No change to Rust source, JNI contract, crypto, storage, preference keys or key handling. Full RELRO, BIND_NOW, 16 KB LOAD alignment, the export check and the build-path leak check stay. No new dependency.
- **Verify**: Rebuild. Then run `llvm-readelf -d` on the stripped .so and check the RELR tag. Run CoreSmokeTest on the emulator: it loads the .so and calls initialize. A RELR load failure is immediate and deterministic at System.loadLibrary. Artifact note: the APK is versionName 0.2.8 (same as the build file), but it was built before HEAD 0842c4e. That commit only removes a 10 KB library, so the numbers above do not change.
- **Effort**: S. **Risk**: low. **Net lines**: about +2 (estimate).
- **Verified**: `scripts/build-rust.zsh` (full fat-LTO rebuild, the new RELR check passes), `./gradlew :app:testDebugUnitTest :app:assembleDebug` and `./gradlew :app:assembleRelease` pass. `llvm-readelf -d` on the stripped .so and on the .so in the release APK: RELR tag, RELRSZ 9008, RELASZ 336 (was 729240); BIND_NOW, FLAGS_1 NOW, GNU_RELRO, 16 KB LOAD Align and the JNI exports stay. .so 10,405,496 B -> 9,684,712 B, release APK 14,059,949 B -> 13,339,165 B (-720,784 B, about -5 %). `zipalign -c -P 16` passes. Not checked: CoreSmokeTest and a load of the .so on an emulator or a device.
- **Status**: applied

### OMBRA-OPT-05: Clear the UI status when the :vpn process dies

- **What**: When the :vpn process dies (Rust uses panic = abort), onServiceDisconnected calls lost(). lost() clears only the binder and the unread connected flag. statusState keeps the last push. So the Connect screen keeps 'Protected', the exit and frozen stats while the TUN is gone. This lasts until Android restarts CoreService and the new process pushes a snapshot: about 1 s after one crash, and longer after repeated crashes because of the restart back-off (estimate).
- **Where**: app/src/main/java/app/ombra/data/CoreClient.kt:103 (onServiceDisconnected), :158-162 (lost); app/src/main/java/app/ombra/ui/AppViewModel.kt:32-36 (stageOf)
- **Change**: In onServiceDisconnected only (not in unbind), also set `statusState.value = null`. stageOf(null) then gives Loading, and the existing Startup screen shows 'The VPN service does not answer' after 8 s. The restarted process pushes a fresh status when it binds again. The removal of the unread `connected` flow moves to OMBRA-OPT-08, so this change stays one behaviour change.
- **Benefit**: After a :vpn crash, the UI no longer shows 'Protected' for a tunnel that does not exist. The change uses the existing Startup state again.
- **Evidence**: CoreClient.kt:158-162 lost() does not touch statusState. stageOf(null) is the normal cold-start path, so it is already exercised. OmbraApp.kt Startup() and strings_ui.xml:170-171 already handle status == null. OnboardingViewModel.onStatus ignores null. The ViewModels are scoped to the activity, so they survive the stage switch. onServiceDisconnected runs only on process death while the UI is bound. git blame CoreClient.kt: b8bff8c only. No DESIGN decision keeps the stale status.
- **Safety**: Only the UI copy of pushed state changes. No change to stored data, IPC format, preference keys or key handling. No security-review lines. No dependency.
- **Verify**: Side effect: after a :vpn crash the main shell leaves composition, so the user comes back to Connect. This is acceptable after a crash. On the emulator: connect, open Connect, run `adb shell am kill` or kill the :vpn pid. Check that the screen leaves 'Protected' and comes back with the new status. ### OMBRA-OPT-06: Do not crash :vpn when the 'VPN wanted' marker file cannot be created

- **What**: `VpnWanted.value = true` calls `file.createNewFile()`. On Android, createNewFile throws IOException for every errno except EEXIST, for example ENOSPC on a full f2fs /data. OmbraVpnService.connect() runs this setter on the :vpn main thread from onStartCommand, and nothing catches the exception, so the :vpn process crashes. This occurs only when the marker is absent (the VPN was off). Every other disk write on this path already tolerates failure. On a full disk, this marker is the only thing that blocks a connect. An always-on start after the user disconnected becomes a crash loop, and without lockdown, traffic then goes out unprotected.
- **Where**: app/src/main/java/app/ombra/vpn/VpnWanted.kt:21-25 (value setter); app/src/main/java/app/ombra/vpn/OmbraVpnService.kt:170-171 (connect, called from onStartCommand:77)
- **Change**: In the setter, catch IOException around `file.createNewFile()`, log only the exception class with Log.w, and still set state.value. Add one VpnWantedTest case: `VpnWanted(File(missingDir, FILE_NAME)).value = true` does not throw, and value is true.
- **Benefit**: On a full disk, Connect, the tile, shortcuts and the always-on start work and do not crash-loop :vpn. Only the sticky restore after a later process death is lost while the disk stays full.
- **Evidence**: VpnWanted.kt:23 `if (value) file.createNewFile() else file.delete()`. OmbraVpnService.kt:171 `CoreHost.vpnWanted = true` runs before launchCore. CoreHost.kt:111-115 forwards to the setter. KeystoreVault.kt:80-94 store() catches Exception ('Never throws'). rust/obscura-core/src/config/mod.rs:35-38: the core logs config save errors and continues. git blame VpnWanted.kt: all b8bff8c; no 'Report:' commit in its history.
- **Safety**: The file name, its location and its meaning (exists = wanted) stay the same, so existing installs read the same state. Only the failure path changes. This is not security-review code and not key or storage-format handling. No dependency.
- **Verify**: The JVM test covers the change: createNewFile with a missing parent directory throws IOException. The trigger is narrow (marker absent, disk full, mainly f2fs), so impact is low.
- **Effort**: S. **Risk**: low. **Net lines**: about +5 (estimate).
- **Status**: approved

### OMBRA-OPT-10: Keep in-flight core requests alive when the UI unbinds; fail them only when :vpn dies

- **What**: MainActivity.onStop calls CoreClient.unbind(), and unbind() calls lost(), which fails every pending request with DISCONNECTED. MainActivity has no configChanges, so a rotation, a dark-mode switch or a window resize also runs onStop. In :vpn, CoreService runs the request in CoreHost.scope and sends the reply to the IResultCallback binder, but the UI has already dropped it. Result: a false 'The VPN service does not answer. Try again.' for Create account, Login, Delete account, a settings change (SettingsEditor also rolls back its value) and the debug bundle (the page shows Failed, but the zip exists). On the Create screen, the error invites a second tap while the first request still runs in :vpn. Nothing serializes create requests, so the user can create a second Obscura account, and the UI can show number 2 while the device is on number 1.
- **Where**: app/src/main/java/app/ombra/data/CoreClient.kt:120-130 (unbind), :133-156 (request), :158-162 (lost), :165-175 (PendingCall); app/src/main/java/app/ombra/ui/MainActivity.kt:92-95 (onStop); app/src/main/java/app/ombra/ui/settings/AccountViewModel.kt:60 (reveal), :76-80 (addTime)
- **Change**: In CoreClient, unbind() no longer fails pending calls. Make PendingCall an IBinder.DeathRecipient. Before `remote.call()`, call `remote.asBinder().linkToDeath(call, 0)`, and fail the call with DISCONNECTED if that throws. binderDied() calls fail(DISCONNECTED). Unlink in onResult and in invokeOnCancellation, because the binder keeps a strong reference to the recipient. Remove the `pending` set and the loop in lost(). Required to keep the OMBRA-SEC-003 rule: in AccountViewModel.reveal() and addTime(), use the reply only if `unlocked` is still true, because ON_STOP runs endVisit() before MainActivity.onStop runs unbind().
- **Benefit**: A rotation, theme switch or short app switch during Login, Create account, Delete, a settings change or a debug bundle no longer gives a false error. No retry creates a second Obscura account. A request still fails at once when the :vpn process dies; in all other cases REQUEST_TIMEOUT (3 min) applies. Limit: with the VPN off, Android can freeze a cached :vpn while the screen is off; the work continues on return.
- **Evidence**: CoreClient.kt:128-129 unbind() -> lost(); :161 `pending.toList().forEach { it.fail(IpcError.DISCONNECTED) }`. CoreService.kt:49-53 runs the request in CoreHost.scope and delivers it to cb. AndroidManifest.xml:40-53: no configChanges and no screenOrientation. ## Areas in good shape

- UI cold start is lean. There is no Application subclass and only two androidx.startup initializers run. The first frame does not wait for :vpn. OMBRA-PERF-001 is not proposed again, because it stays Skipped and there is still no measurement.
- IPC does no extra work. Rust increments Status.version only on a real change. Pushes are versioned and gzip-compressed, and binder threads decode them. Collectors exist only while CoreService is bound (OMBRA-PERF-004).
- Battery: there is one 1 Hz stats poll, and it runs only while the tunnel is connected and Connect is visible. The 12 h refresh uses a coroutine delay. There are no WorkManager jobs, no wake locks and no wakeup alarms. The clipboard-clear alarm is inexact and non-wakeup, and comes from the security review.
- Lifecycle: every network callback, receiver and scope has a matching unregister or cancel. The UI collects with collectAsStateWithLifecycle and WhileSubscribed.
- JNI boundary: each Rust-to-Java callback catches Throwable. Each future completes with an error code. Main code has no runCatching, no `!!` and no unchecked casts.
- Binder sizes stay under the limit (gzip budget, one ordered ombra-ipc thread, snapshots for new listeners).
- Process death and upgrade: START_STICKY, the MY_PACKAGE_REPLACED restore and a Navigator saver that drops unknown routes. The TUN build fails closed. A corrupt settings.json falls back to privacy-safe defaults.
- Lists and Compose: work runs on Default or IO, rows have stable keys and contentType, the icon cache is bounded. Animations are read in the draw phase and stop under Remove animations.
- Dependencies: only AndroidX, Compose, navigation3, lifecycle, coroutines, serialization and profileinstaller. There is no third-party library.
- R8 full mode with narrow JNI keep rules. The build strips Log v/d/i. Packaging leaves out metadata files. The build ships arm64 only, with the .so uncompressed and 16 KB aligned.
- Resources: code references all 448 strings. There are no unused drawables or raw files, except the two duplicate icons in OMBRA-OPT-08.
- Rust release profile: fat LTO, 1 codegen unit, panic=abort, stripped, offline frozen build. The TUN reader is event-driven, and config writes occur only on a real change.
- Abstractions: CoreSource, CoreChannel and TunnelControl each have a second real implementation, so they are not over-abstraction.
- UI/UX: the connect control is accessible. Loading, empty and error states exist. There is one back model with predictive back. Confirmations match the risk, keyboards fit each input, and the app uses Material 3 Expressive.
